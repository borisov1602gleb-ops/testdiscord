# Аналог Discord для России — полное описание проекта для Claude Code

Это самодостаточный документ: вся информация о продукте, аналитике, архитектуре и
задачах на разработку в одном месте. Ничего дополнительно читать не нужно.

---

## 1. Продукт

### 1.1 Контекст
После блокировки Discord на территории РФ возникла потребность в удобной платформе
для тематического общения, ориентированной в первую очередь на геймерское
сообщество. Существующие российские аналоги (Макс, ВК Звонки, Телемост, Sber Jazz
и др.) позиционируются преимущественно как инструменты для голосовых и
видеозвонков для созвонов «по работе», не требующие долгой демонстрации экрана
или сложного функционала потокового асинхронного общения, что не закрывает
потребность в регулярной коммуникации по интересам.

### 1.2 Суть проекта
Платформа, в которой акцент смещён с функции «звонилки» на удобную организацию
тематических сообществ: пользователи объединяются по интересам и общаются в
удобном асинхронном и синхронном форматах. Ключевой принцип — общение должно быть
добровольным и комфортным: без навязчивых уведомлений и принудительных звонков.

### 1.3 Конкурентный анализ
Основные игроки на российском рынке сосредоточены на замене звонковой
функциональности Discord, но не воспроизводят его модель каналов — систему
серверов, каналов, ролей и тематических разделов. Именно эта модель делает
Discord удобным для регулярного общения, и именно её отсутствие у конкурентов
создаёт рыночную возможность.

### 1.4 Перспективы развития (не входит в MVP)
В дальнейшем подразумевается интеграция стримингового функционала (аналог Twitch,
также недоступного в РФ), что позволит объединить текстовое, голосовое и
видеоконтентное общение.

## 2. North Star метрика

**WECU (Weekly Engaged Community Users)** — уникальные пользователи за неделю,
которые в сообществе перешли порог значимой активности. Пользователь считается
вовлечённым (engaged), если в течение недели он достиг порога значимой активности
в сообществе: отправил ≥ N сообщений или принял участие в звонке в течение как
минимум M минут. Пороговые значения предполагается валидировать на исторических
данных.

Драйверы: DAU текстового общения, DAU звонковых сессий, количество активных
сообществ, количество групповых звонковых сессий, суммарная продолжительность
групповых звонковых сессий, перцентильные длительности звонковых сессий,
количество сообщений на активного пользователя.

## 3. Защитные метрики

- **Community Retention** — доля новых пользователей, вернувшихся в то же
  сообщество через 7/30 дней. Защищает от роста WECU за счёт одноразовых
  инвайтов без продолжительного общения.
- **Activation Rate** — доля пользователей, совершивших значимое действие
  (по WECU) в течение N времени после вступления.
- **Доля раннего покидания сообщества** — доля участников, покинувших сообщество
  спустя K дней; сигнализирует о случайных/спам-участниках.
- **Доля технических ошибок** — ошибки при звонке, ошибки отправки сообщений,
  особенно в воронке регистрации и присоединения к сообществам.

## 4. Продуктовая гипотеза

Если дать возможность присоединиться к звонковой сессии напрямую по ссылке без
обязательной регистрации, то снизится порог входа в коммуникацию: увеличится
конверсия из открытия приглашения в успешное подключение к звонковой сессии, а
для новых пользователей это может вести к последующей регистрации и
присоединению к сообществу. Метрика-воронка: доля пользователей, открывших
приглашение, которые успешно присоединились к звонковой сессии (и далее к
сообществу).

## 5. User-flow (продукт)

1. Создание ссылки-приглашения
2. Открытие ссылки-приглашения
3. Присоединение к звонковой сессии
4. Общение
5. Тип пользователя: новый → регистрация ИЛИ существующий → вход
6. Присоединение к сообществу
7. Активация (значимое действие по WECU)
8. Вовлечение в сообществе
9. Ретеншен (возвращение)
10. Проверка технических ошибок и мониторинг раннего выхода из сообщества

## 6. Архитектура данных

### 6.1 Ключевые события пользователя

| Событие | Смысл | Обязательные поля |
|---|---|---|
| `invite_link_opened` | Открытие приглашения | event_id, timestamp, invite_id, community_id, anonymous_id/user_id, device_id |
| `call_joined` | Подключение к звонку | event_id, timestamp, call_id, community_id, anonymous_id/user_id, invite_id, join_status (success/failed) |
| `registration_completed` | Завершение регистрации | event_id, timestamp, user_id, anonymous_id, registration_source, invite_id, community_id |
| `community_joined` | Вступление в сообщество | event_id, timestamp, user_id, community_id, invite_id, join_source |
| `message_sent` | Отправка сообщения | event_id, timestamp, user_id, community_id, channel_id, message_id |
| `call_participated` | Участие в звонке | event_id, timestamp, user_id, community_id, call_id, duration_sec |

**Важно**: `message_sent` и `call_participated` — два отдельных события с полным
набором обязательных полей каждое. Изначально в задании было одно событие
`community_interaction` с условным полем `duration_sec` («заполняется только для
звонков») — это антипаттерн: структура события не должна меняться в зависимости
от типа действия. Используем разделённую версию.

**Важно про invite_id**: `invite_id ≠ event_id`. `event_id` — первичный ключ
события. `invite_id` — внешний ключ, НЕ уникален по событиям: на один инвайт
может приходиться множество событий `invite_link_opened` и `call_joined` от
разных пользователей (и даже одновременно). Поэтому `invites` — отдельная
таблица-справочник (см. раздел 7), а не просто поле внутри события. Число
использований инвайта считается агрегацией по логу событий
(`COUNT(*) GROUP BY invite_id`), а не мутируемым счётчиком на самой записи
инвайта — иначе возможна гонка при одновременном подключении нескольких
пользователей по одной ссылке.

### 6.2 Проверки качества данных

- **Полнота** — для каждого события обязательны `event_id`, `timestamp` и
  идентификатор пользователя (`user_id` либо `anonymous_id`); для действий в
  сообществе — `community_id`. Допустимого null rate нет.
- **Уникальность** — `event_id` не повторяется. Дубли удаляются на серебряном
  слое, исходные записи сохраняются в бронзовом, конфликтные записи
  отправляются в карантин.
- **Допустимость и согласованность** — `action_type` ∈ {message, call},
  `duration_sec` ≥ 0, `join_status` ∈ {success, failed}, `invite_id` и
  `community_id` должны существовать в справочниках. Некорректные значения не
  попадают в витрину.

### 6.3 Схема слоёв: Bronze → Silver → Gold

- **BRONZE** — сырые события из приложения, сервиса звонков и backend, без
  изменений, с `event_id`, `timestamp` и техническими атрибутами (источник,
  время получения). Ничего не валидируется и не отбрасывается.
- **SILVER** — проверка контракта, дедупликация по `event_id`, единый UTC,
  нормализация ID, связка `anonymous_id` и `user_id` после регистрации,
  проверка enum-полей и справочников. Ошибки → карантин (не удаляются молча).
- **GOLD** — итоговая витрина: конверсии воронки (открытие invite → подключение
  к звонку → регистрация → вступление в сообщество → вовлечение), WECU,
  Activation Rate, D7/D30 Community Retention, доля технических ошибок.

**Для MVP-разработки**: реализуется только запись в Bronze (таблица
`events_bronze`, см. схему БД). Silver/Gold ETL — отдельный процесс, не входит в
объём backend-разработки на этом этапе.

### 6.4 Приватность / PII
Событие `registration_completed` связано с email. Сырой email не должен
попадать в событийный payload как есть без необходимости — если возможно,
использовать `user_id` как основной идентификатор в событиях, email хранить
только в таблице `users`.

## 7. Схема базы данных продукта

Это таблицы состояния приложения (отдельно от `events_bronze` — аналитического лога).

| Сущность | Поля |
|---|---|
| `users` | id (PK), email (unique), registration_source, created_at |
| `communities` | id (PK), name, owner_id (FK → users), created_at |
| `invites` | id (PK), community_id (FK), created_by (FK → users), expires_at, max_uses, use_count, created_at |
| `community_members` | id (PK), community_id (FK), user_id (FK), role (owner/member), invite_id (FK → invites, nullable), joined_at — уникальность по (community_id, user_id) |
| `channels` | id (PK), community_id (FK), name, type (text/voice), created_at |
| `messages` | id (PK), channel_id (FK), user_id (FK), content, created_at |
| `calls` | id (PK), channel_id (FK), started_at, ended_at |
| `call_participants` | id (PK), call_id (FK), user_id (FK, nullable — гость), anonymous_id (nullable), joined_at, left_at, duration_sec |
| `login_codes` | id (PK), email, code, expires_at, used, created_at |
| `events_bronze` | event_id (PK), event_type, payload (jsonb), received_at, source |

Связи: `users` 1—N `communities` (владение); `users`+`communities` 1—N
`community_members`; `community_members.invite_id` → `invites.id`; `communities`
1—N `channels`; `channels` 1—N `messages`/`calls`; `calls` 1—N
`call_participants`.

## 8. Архитектура системы

Клиент (веб-приложение) обращается к единому Backend API, который параллельно
работает с тремя направлениями:
1. **PostgreSQL** — основная БД продукта (раздел 7)
2. **Сервис звонков** — LiveKit (SFU) + coturn (TURN/STUN)
3. **events_bronze** — запись аналитических событий (раздел 6)

Одно и то же действие пользователя (например, подключение к звонку) одновременно
отражается в состоянии приложения (БД), в звонковом соединении и в
аналитическом логе.

## 9. Технический стек (self-hosted, без сторонних SaaS API)

| Компонент | Технология | Почему |
|---|---|---|
| Backend | Node.js (Express) | свой код, весь в репозитории |
| База данных | PostgreSQL (Docker) | open-source, self-host |
| Реалтайм-чат | WebSocket (Socket.io) | не требует внешних сервисов |
| Звонки — SFU | LiveKit (self-hosted, Docker) | open-source SFU для групповых звонков |
| Звонки — TURN/STUN | coturn (self-hosted, Docker) | open-source, прохождение NAT |
| Email (код на почту) | SMTP-заглушка на этапе MVP → Яндекс.Почта для домена в проде | без стороннего API |
| Оркестрация | docker-compose | весь стек одной командой |

## 10. Объём MVP

### Входит
- Регистрация/вход по коду на email (без пароля)
- Создание сообщества, автоматически один текстовый и один голосовой канал
- Текстовые сообщения в реальном времени (WebSocket)
- Групповой звонок в голосовом канале (аудио, без видео)
- Инвайт-ссылка: подключение к звонку без регистрации с последующим
  предложением зарегистрироваться
- Роль: owner / member (без кастомных ролей и прав)
- Логирование всех 6 событий из раздела 6.1 в `events_bronze`

### Не входит (откладывается)
Видео и демонстрация экрана, кастомные роли, множественные каналы, стриминг,
модерация/банлисты, push-уведомления, мобильное приложение.

## 11. UX / user flow для дизайна

1. Пользователь A создаёт сообщество → создаёт инвайт-ссылку
2. Пользователь B открывает ссылку → превью сообщества + кнопка «Присоединиться
   к звонку» (без регистрации)
3. B подключается к звонку → общается
4. В звонке / после — предложение зарегистрироваться, чтобы остаться в
   сообществе
5. B регистрируется по коду на почту (или продолжает как гость без сохранения
   истории)
6. После регистрации B автоматически становится участником сообщества
7. B пишет сообщение / участвует в звонках → вовлечение

Экраны: превью инвайта, экран звонка (список участников, mute/unmute), экран
регистрации по коду, главный экран сообщества (каналы + чат), настройки
инвайтов.

## 12. Конкретные задачи на реализацию (backend + БД)

### 12.1 Создать схему БД
Все таблицы из раздела 7, с внешними ключами и ограничениями (UUID
первичные ключи, `type` в `channels` только text/voice, `role` в
`community_members` только owner/member).

### 12.2 Реализовать API-эндпоинты

| Метод | Путь | Логика |
|---|---|---|
| POST | `/auth/send-code` | генерирует код, пишет в `login_codes`, rate-limit 60 сек/email |
| POST | `/auth/verify-code` | проверяет код, создаёт/находит `user`; если передан `anonymous_id` — привязывает его прошлые `call_participants` к новому `user_id`; если новый юзер — событие `registration_completed` |
| POST | `/communities` | создаёт сообщество + владельца в `community_members` + два канала (text/voice) |
| GET | `/communities/:id` | сообщество + список каналов |
| POST | `/invites` | создаёт инвайт |
| GET | `/invites/:id` | отдаёт данные инвайта + событие `invite_link_opened` |
| POST | `/invites/:id/join` | добавляет в `community_members`, инкрементит `use_count`, событие `community_joined` |
| POST | `/calls` | создаёт звонковую сессию для канала |
| POST | `/calls/:id/join` | добавляет в `call_participants` (поддержка `anonymous_id` без `user_id`), событие `call_joined` с `join_status` |
| POST | `/calls/:id/leave` | считает `duration_sec`, событие `call_participated` (только для зарегистрированных user_id) |
| POST | `/messages` | создаёт сообщение, событие `message_sent` |
| GET | `/messages?channel_id=` | история сообщений |

### 12.3 Логирование событий
Общая функция `logEvent(type, payload, source)`, которая генерирует `event_id`
и `timestamp`, пишет запись в `events_bronze` без валидации содержимого
(Bronze-принцип — фиксируем как есть).

### 12.4 Известный edge case — обязательно обработать
Гость подключается к звонку анонимно (`anonymous_id`, без `user_id`) → потом
регистрируется → при выходе из звонка должна корректно посчитаться
`duration_sec`, а не потеряться. Решение: при регистрации выполнить
`UPDATE call_participants SET user_id = ... WHERE anonymous_id = ... AND user_id IS NULL`
до попытки записать `registration_completed`.

### 12.5 Docker Compose
`docker-compose.yml`, поднимающий: `postgres` (с применением схемы при старте),
`backend`, `livekit` (dev-режим), `coturn`. Backend — на порту 3000.

## 13. Критерий готовности

Полный сценарий должен проходить end-to-end без ошибок:
создание сообщества → создание инвайта → открытие инвайта гостем → подключение
гостя к звонку без регистрации → регистрация гостя по коду → вступление в
сообщество через тот же инвайт → выход из звонка с корректным `duration_sec` →
отправка сообщения.

После прогона в таблице `events_bronze` должны быть записи всех 6 типов
событий из раздела 6.1 с корректно заполненными обязательными полями.
