Документ описывает платформу тематических сообществ на момент последнего
коммита ветки `claude/amazing-goodall-gfhr4z`. Здесь всё: что работает, как
устроено внутри, что проверено, что осознанно не сделано и куда двигаться
дальше.

Рядом лежат два других документа:

- [`PROJECT_FULL_SPEC.md`](PROJECT_FULL_SPEC.md) — исходная спецификация
  продукта (задание), по которой всё написано;
- [`../README.md`](../README.md) — короткая инструкция: как запустить, какие
  есть эндпоинты, где смотреть статистику.

## 1. Коротко

Работающий MVP: сообщества с текстовыми и голосовыми каналами, вход по коду
на почту без пароля, чат в реальном времени, групповые звонки с камерой и
демонстрацией экрана, приглашение гостя в звонок без регистрации и
аналитика на трёх слоях данных с экраном для владельца сообщества.

| Параметр | Значение |
|---|---|
| Состояние | MVP работает целиком, критерий готовности из раздела 13 спецификации проходит |
| Кода | ~4250 строк JS (backend + клиент), ~1970 строк CSS, ~2400 строк SQL |
| Таблиц в базе | 19: 9 продуктовых + 10 аналитических |
| HTTP-эндпоинтов | 17 + проверка здоровья |
| Автоматических проверок | 4 набора, ~50 утверждений, гоняются в GitHub Actions на каждый push |
| Не сделано | оплата, роли сложнее owner/member, модерация, мобильное приложение, магазин расширений |

## 2. Как запустить

### Windows без Docker (как запускается сейчас)

```powershell
.\start.ps1
```

Скрипт поднимает службу PostgreSQL, при первом запуске спрашивает пароль
пользователя `postgres` и сохраняет настройки в `backend\.env` (файл не
попадает в репозиторий), создаёт базу и применяет схему, если их нет,
ставит зависимости и запускает backend. Повторный запуск безопасен.

Если PowerShell отказывается выполнять скрипт:

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

### Docker

```bash
docker compose up --build
```

Поднимаются `postgres`, `backend`, `livekit` в dev-режиме и `coturn`.

### Вручную

```bash
createdb community && psql -d community -f db/schema.sql
cd backend && npm install
DATABASE_URL=postgres://postgres:postgres@localhost:5432/community \
EXPOSE_DEV_CODE=true npm start
```

Миграции из `db/migrations` и схема аналитических слоёв применяются
автоматически при старте backend — отдельного шага не нужно.

Интерфейс и API живут на одном адресе: http://localhost:3000

## 4. Архитектура

Один процесс Node.js обслуживает всё: HTTP API, WebSocket поверх того же
сервера и раздачу статики клиента. Отдельного веб-сервера и сборки нет —
клиент написан на ванильных ES-модулях.

```
Браузер ──HTTP──►  Backend (Express)  ──► PostgreSQL     состояние продукта
        ──WS────►  Socket.IO          ──► events_bronze  аналитический лог
        ──WebRTC─►  LiveKit (SFU)                        звук и видео мимо backend
                    coturn                                прохождение NAT
```

Важная деталь: **звук идёт мимо backend**. Backend только выдаёт токен
доступа к комнате, а дальше браузер общается с LiveKit напрямую. Поэтому
даже если сервер звонков недоступен, учёт участия остаётся корректным — на
выходе длительность всё равно посчитается.

### Как выглядит одно действие

Подключение к звонку затрагивает три вещи одновременно:

1. клиент просит токен: `POST /calls/:id/join`;
2. backend записывает участника в `call_participants`, пишет событие
   `call_joined` в аналитический лог и отдаёт токен LiveKit;
3. браузер подключается к LiveKit и начинает передавать звук.

Отказ на третьем шаге не рушит первые два — это осознанное разделение.

### Гость и пользователь — один человек

До регистрации человек существует только как `anonymous_id` в браузере. При
входе по коду backend привязывает его прошлые записи участия к появившемуся
`user_id` **до** записи события о регистрации — иначе длительность участия
потерялась бы (это отдельно оговорённый в спецификации случай 12.4). В
аналитике те же две личности склеиваются в одного человека.

## 6. API

Авторизация — заголовок `Authorization: Bearer <токен>` из `/auth/verify-code`.

| Метод | Путь | Кто может | Что делает |
|---|---|---|---|
| POST | `/auth/send-code` | все | Отправляет код на почту, не чаще раза в минуту на адрес |
| POST | `/auth/verify-code` | все | Проверяет код, создаёт или находит пользователя, привязывает гостевое участие, выдаёт токен |
| GET | `/users/me` | вошедший | Профиль |
| PATCH | `/users/me` | вошедший | Меняет имя и скрытие почты |
| GET | `/communities` | вошедший | Свои сообщества |
| POST | `/communities` | вошедший | Создаёт сообщество, владельца и два канала |
| GET | `/communities/:id` | участник | Сообщество, каналы и роль запросившего |
| GET | `/communities/:id/analytics` | владелец | Метрики из витрин Gold |
| POST | `/communities/:id/analytics/refresh` | владелец | Прогоняет ETL и отдаёт пересчитанные метрики |
| POST | `/invites` | участник | Создаёт приглашение |
| GET | `/invites/:id` | все | Превью приглашения, выдаёт гостю `anonymous_id` |
| POST | `/invites/:id/join` | вошедший | Вступление в сообщество |
| POST | `/calls` | участник или гость с приглашением | Создаёт звонковую сессию в голосовом канале |
| POST | `/calls/:id/join` | участник или гость с приглашением | Добавляет участника и выдаёт токен LiveKit |
| POST | `/calls/:id/leave` | участник звонка | Считает длительность, при необходимости завершает звонок |
| POST | `/messages` | участник | Отправляет сообщение и рассылает его по WebSocket |
| GET | `/messages?channel_id=` | участник | История сообщений |
| GET | `/health` | все | Проверка доступности базы |

### Реалтайм

Подключение: `io('http://localhost:3000', { auth: { token } })`. Без
действующего токена соединение отклоняется. События: `join_channel` и
`leave_channel` с идентификатором канала (членство проверяется), входящее
`message`.

Источник правды — HTTP-маршрут: сообщение сначала пишется в базу и только
потом рассылается. Если WebSocket отвалился, сообщение не теряется.

## 7. Аналитика: три слоя

Спецификация задаёт шесть продуктовых событий и схему Bronze → Silver →
Gold. Реализовано всё три слоя.

### События

`invite_link_opened`, `call_joined`, `registration_completed`,
`community_joined`, `message_sent`, `call_participated`.

Все пишутся через единственную функцию `logEvent(type, payload, source)`
(`backend/src/lib/events.js`): она добавляет `event_id` и время и сохраняет
payload без валидации — это и есть принцип Bronze. Сбой записи события
логируется, но не ломает действие пользователя.

### Bronze

Сырой лог. Ничего не проверяется и не отбрасывается. Единственная таблица
`events_bronze`.

### Silver

Очистка (`backend/src/etl/silver.js`):

- payload разбирается в типизированные колонки; функции `silver_uuid`,
  `silver_int`, `silver_ts` возвращают NULL вместо падения на мусоре;
- `community_id` восстанавливается по каналу или звонку — в событии
  неудачного подключения его может не быть вовсе;
- `identity_map` связывает гостя с пользователем, причём **задним числом**:
  события, уже загруженные под анонимным идентификатором, переписываются;
- негодное событие не теряется, а уезжает в карантин с причиной:

| Причина | Что не так |
|---|---|
| `unknown_event_type` | Тип не из шести описанных |
| `bad_uuid` | Идентификатор есть, но это не UUID |
| `no_person` | Нет ни `user_id`, ни `anonymous_id` |
| `bad_enum` | `join_status` не `success` и не `failed` |
| `unknown_reference` | `community_id` или `invite_id` нет в справочнике |
| `bad_duration` | Длительность отрицательная, нечисловая или больше суток |
| `bad_timestamp` | Время не разбирается или из будущего |

Загрузка инкрементальная: берётся всё, чего ещё нет ни в Silver, ни в
карантине. Отметка времени была бы дешевле, но тогда событие, приехавшее
задним числом, молча потерялось бы.

### Gold

Витрины под конкретные вопросы (`backend/src/etl/gold.js`). Пересобираются
целиком на каждом прогоне: данных мало, а полная пересборка исключает
расхождения после приехавших задним числом событий и после склейки личностей.

Что считается:

| Метрика | Как |
|---|---|
| Воронка приглашения | Вложенная и по людям: открыл → зашёл в звонок → вступил, каждый шаг только среди прошедших предыдущий и только вперёд по времени |
| WECU | За неделю: активные — кто сделал значимое действие, вовлечённые — кто перешагнул порог (5 сообщений или 5 минут в звонках) |
| Активация | Доля вступивших, сделавших значимое действие в первые сутки. Владелец не считается: он не вступал |
| Возврат на 7-й день | Доля вступивших больше недели назад, кто вернулся |
| Доля ошибок подключения | Неудачные попытки входа в звонок к общему числу |
| Активность по дням | Сообщения, участия в звонках, секунды, активные люди |
| Длительности звонков | Среднее, медиана, максимум |

### Как запускается

- по расписанию внутри backend, интервал `ETL_INTERVAL_SEC` (по умолчанию
  300 секунд, `0` выключает);
- вручную: `cd backend && npm run etl`;
- кнопкой «Пересчитать» на экране аналитики.

Прогон — одна транзакция под блокировкой уровня транзакции, поэтому
расписание и кнопка не накладываются друг на друга.

### Где смотреть

- **В интерфейсе**: колонка каналов → «Управление» → «Аналитика»
  (`#/c/:id/analytics`). Виден только владельцу, сервер проверяет это сам.
- **Запросами**: `psql -U postgres -d community -f db/analytics.sql` —
  11 готовых запросов, первые 7 по сырому Bronze, остальные по слоям.

## 8. Клиент

Ванильные ES-модули, хеш-роутинг, без сборщика и зависимостей.

| Файл | Ответственность |
|---|---|
| `js/app.js` | Точка входа, перехват необработанных сбоев |
| `js/router.js` | Хеш-роутинг, маршруты с пометкой «доступен гостю» |
| `js/api.js` | HTTP-клиент, перевод кодов ошибок в человеческий текст |
| `js/store.js` | Токен, пользователь, гостевой идентификатор, текущий звонок |
| `js/dom.js` | Безопасное построение DOM и иконки |
| `js/settings.js` | Настройки устройств и звуков в браузере |
| `js/views/` | Экраны: login, home, invite, call, settings, analytics |
| `styles.css` | Дизайн-система Nocturne: все значения в переменных `:root` |

Два принципа, которые стоит соблюдать дальше:

1. **Никакого `innerHTML`.** Весь пользовательский текст попадает в DOM
   только через `textContent` — иначе имя сообщества или сообщение станут
   способом подсунуть чужой код.
2. **Значения оформления — в переменных.** Меняя `:root`, меняешь вид
   целиком; отдельных цветов по месту нет.

## 9. Тесты и CI

Четыре набора, все гоняются в GitHub Actions на каждый push и pull request
(`.github/workflows/tests.yml`): поднимается PostgreSQL, применяется схема,
стартует backend, прогоняются проверки. При падении в лог выводится вывод
backend.

| Набор | Что проверяет | Проверок |
|---|---|---|
| `scripts/e2e-test.sh` | Критерий готовности целиком: сообщество → приглашение → гость в звонке → регистрация → вступление → выход с длительностью → сообщение → все 6 типов событий на месте | 12 шагов |
| `scripts/edge-cases-test.sh` | Права доступа и граничные случаи: кто куда не должен попадать, исчерпанное приглашение, чужое участие, длинное сообщение, битый JSON, перебор кода | 22 |
| `backend/scripts/etl-test.mjs` | Слои на заведомо грязных данных: карантин с правильной причиной, отсутствие задвоения, склейка гостя, корректность витрин | 19 |
| `backend/scripts/ws-test.mjs` | Доставка по WebSocket и отказ без токена | 2 |

Запуск вручную:

```bash
PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres ./scripts/e2e-test.sh
./scripts/edge-cases-test.sh
cd backend && node scripts/etl-test.mjs
cd backend && node scripts/ws-test.mjs
```

Первые три требуют запущенный backend с `EXPOSE_DEV_CODE=true`; проверке
слоёв достаточно доступа к базе — она создаёт временное сообщество и
убирает его за собой.

| Аналитика для владельца | Экран с воронкой, вовлечённостью, активацией, возвратом, ошибками и активностью по дням |
| Слои Silver и Gold | ETL, очистка, карантин, склейка личностей, витрины; экран стал читать витрины вместо сырого лога |

| Запускалка для Windows | `start.ps1` — запуск одной командой |

## 11. Что нашли на ревью и починили

Сверка кода со спецификацией и проверка живыми запросами вскрыли семь мест,
где система вела себя не так, как обещала.

| Проблема | Чем грозила | Как закрыта |
|---|---|---|
| Событие с несуществующим `user_id` роняло ETL на внешнем ключе | Bronze принимает что угодно, значит рано или поздно такое событие появится — и вся аналитика замирает без единой жалобы | Такие записи не участвуют в склейке личностей |
| Посторонний мог закрыть чужое участие в звонке | Чужая длительность обнулялась, звонок мог завершиться | У вошедшего участие ищется только по его `user_id` |
| Гость входил в звонок по исчерпанному приглашению | Превью той же ссылки показывало её недействительной — поведение противоречило само себе | Лимит использований проверяется и при входе в звонок |
| Код входа можно было перебирать | Шестизначное число и десять минут жизни: ограничение стояло только на отправку, не на проверку | Счётчик попыток, после пяти ошибок код гаснет |
| «Один звонок на канал» держалось только на коде | При одновременных запросах участники попали бы в разные комнаты | Уникальный индекс в базе; миграция сначала закрывает лишние незавершённые звонки |
| Длина сообщения не ограничена | Мегабайтное сообщение в базе и у всех в канале; больше 100 КБ отдавало «внутреннюю ошибку сервера» | 2000 символов, тело запроса 100 КБ, понятные коды 400 и 413 |
| Мусор в дате и отрицательный `limit` давали 500 | Ошибка клиента маскировалась под сбой сервера | Валидация на входе, ошибки клиента возвращают 400 |

Плюс два требования спецификации по качеству данных, которых не было в
Silver: перечисление `join_status` и существование `community_id` и
`invite_id` в справочниках.

## 12. Отклонения от спецификации

Все осознанные.

| Что | Как в спецификации | Как сделано и почему |
|---|---|---|
| Лимит использований приглашения | Раздел 6.1 предлагает считать агрегацией по событиям, а не счётчиком, из-за гонки | Счётчик `use_count` (он же есть в разделах 7 и 12.2) под блокировкой строки: гонки нет, правило соблюдается точно. В аналитике использования считаются по людям из событий |
| Камера и демонстрация экрана | Раздел 10: не входит в MVP | Сделано: LiveKit умеет и то, и другое, backend менять не пришлось |
| Слои Silver и Gold | Раздел 6.3: ETL не входит в объём этапа | Сделано после MVP — иначе метрики оставались бы приблизительными |
| Таблица `users` | Раздел 7: без имени и приватности | Добавлены `display_name` и `hide_email` — их видят другие участники |
| Таблица `login_codes` | Раздел 7: без счётчика попыток | Добавлен `attempts` — иначе код перебирается за время жизни |
| Таблица `calls` | Раздел 7: без ограничений на параллельные сессии | Добавлен уникальный индекс на активный звонок в канале |

## 13. Известные ограничения

| Ограничение | Почему так и чем чревато |
|---|---|
| `anonymous_id` можно подставить чужой | У гостя нет ничего, чем он мог бы себя подтвердить, — это плата за вход в звонок без регистрации. Идентификатор случайный и лежит в чужом браузере, подобрать нельзя, но защиты от целенаправленной подмены нет |
| Гостевой выход из звонка не подтверждается | По той же причине. У вошедшего пользователя этой дыры нет |
| WebSocket не перепроверяет членство | Право на канал проверяется при подписке. Исключения из сообщества в MVP нет; как появится — подписки надо будет сбрасывать |
| Нет пагинации истории | Отдаются последние 200 сообщений |
| Нет ограничений на создание сообществ и приглашений | Один аккаунт может наплодить их сколько угодно |
| Звонки не проверяются автотестами | CI гоняет логику участия и длительности, но без LiveKit: звук, камера и демонстрация экрана проверяются руками в браузере |
| Минуты гостей не попадают в аналитику | Событие участия пишется только для зарегистрированных (раздел 12.2 спецификации) |

### Перед продом обязательно

1. `JWT_SECRET` — заменить на длинный случайный, иначе токены подделываются.
2. `EXPOSE_DEV_CODE` — выключить: сейчас код входа возвращается в ответе.
3. Настоящий SMTP вместо заглушки, печатающей код в консоль.
4. Ключи LiveKit вместо `devkey`/`secret` и dev-режима.
5. HTTPS: демонстрация экрана работает только в защищённом контексте, а на
   `localhost` это исключение.
6. Сузить `cors()` до своего домена.

## 14. Куда двигаться дальше

### Ближайшее по продукту

Обсуждалась идея сделать платформу настраиваемой под разные аудитории
(репетиторы, рабочие команды), а не добавлять функции под каждый сегмент.
Предлагаемая конструкция:

1. **Модули вместо фич.** Доска, расписание, задачи — это типы каналов со
   своим экраном и своими таблицами, а не отдельные куски продукта. Чат и
   звонок уже устроены именно так.
2. **Договор модуля.** Каждый модуль регистрируется в реестре, хранит своё
   с привязкой к сообществу и каналу, пишет события в общем формате,
   рендерится через таблицу соответствий «тип канала → экран» и спрашивает
   права у общего места.
3. **Пресеты сообществ.** При создании выбирается шаблон («Игровое»,
   «Репетитор», «Рабочая команда»), и нужный набор каналов создаётся сам.
   Новый сегмент — строчка в списке шаблонов, а не новая версия продукта.
4. **Готовое вместо своего.** Доску, документы и задачи дешевле встроить из
   открытых self-hosted решений, чем писать. Подводные камни: единый вход,
   запрет на встраивание в рамку у некоторых сервисов, лицензии AGPL и BSL.
5. **Интеграции по возрастанию сложности**: фид календаря `.ics` → исходящие
   вебхуки → входящие вебхуки → полноценные подключения по OAuth.

Магазин сторонних приложений с песочницей — отдельный большой проект, к
нему стоит идти только когда появятся желающие писать расширения.

### Что заложить в код заранее

1. Типы каналов вынести из жёсткого списка в схеме в справочник — иначе
   каждый новый модуль требует миграции.
2. Завести общий формат событий для модулей, чтобы слой очистки не правился
   под каждый новый.
3. Явно разделить во фронте «рамку» и «содержимое канала».
4. Продумать структуру ролей: `owner`/`member` не хватит для рабочих команд.

### Технический долг

- Silver/Gold считаются полным перебором Bronze. На объёмах MVP это копейки,
  на больших понадобится водяная отметка и секционирование по дате.
- Нет линтера и единого форматирования.
- История сообщений без подгрузки по прокрутке.

## 16. Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | Порт backend |
