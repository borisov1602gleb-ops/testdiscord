# Платформа тематических сообществ — MVP

[![Тесты](https://github.com/borisov1602gleb-ops/testdiscord/actions/workflows/tests.yml/badge.svg)](https://github.com/borisov1602gleb-ops/testdiscord/actions/workflows/tests.yml)

Два документа рядом: [docs/PROJECT_FULL_SPEC.md](docs/PROJECT_FULL_SPEC.md) —
исходная спецификация продукта, по которой всё написано;
[docs/PROJECT_STATE.md](docs/PROJECT_STATE.md) — полное описание состояния
проекта: что сделано, как устроено внутри, что проверено, какие есть
ограничения и куда двигаться дальше. Здесь, в README, — короткая инструкция.

Веб-клиент, backend и инфраструктура MVP по спецификации проекта: сообщества с
текстовыми и голосовыми каналами, вход по коду на email, подключение к звонку по
инвайт-ссылке без регистрации и логирование продуктовых событий в аналитический
слой Bronze.

После `docker compose up` интерфейс открывается на http://localhost:3000 — тот же
сервер отдаёт и API, и клиент.

## Стек

| Компонент | Технология |
|---|---|
| Backend | Node.js 20+ / Express |
| Клиент | Ванильные ES-модули, без сборки |
| База данных | PostgreSQL 16 |
| Реалтайм-чат | Socket.IO (WebSocket) |
| Звонки — SFU | LiveKit (self-hosted, dev-режим) |
| Звонки — TURN/STUN | coturn (self-hosted) |
| Email | SMTP-заглушка (код печатается в лог backend) |
| Оркестрация | docker-compose |

## Запуск

```bash
docker compose up --build
```

Поднимаются `postgres` (схема из `db/schema.sql` применяется при первом старте),
`backend` на порту 3000, `livekit` в dev-режиме (ключи `devkey`/`secret`) и `coturn`.

Проверка: `curl http://localhost:3000/health`

### Запуск на Windows одной командой

```powershell
.\start.ps1
```

`start.ps1` поднимает службу PostgreSQL, при первом запуске спрашивает пароль
пользователя `postgres` и сохраняет настройки в `backend\.env` (файл не
попадает в репозиторий), создаёт базу и применяет схему, если их ещё нет,
ставит зависимости и запускает backend. Повторный запуск безопасен.

Если PowerShell отказывается выполнять скрипт, нужно один раз разрешить
запуск локальных скриптов:

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

### Локальный запуск без Docker

Пригодится, если образы Docker Hub недоступны.

Миграции из `db/migrations` и схема аналитических слоёв применяются
автоматически при старте backend (`backend/src/lib/schema.js`): все файлы
написаны идемпотентно, поэтому обновление кода не требует отдельного шага.
Изменение, которое нельзя сделать идемпотентным (переименование колонки,
перенос данных), так не проходит — такое применяется руками.

```bash
createdb community && psql -d community -f db/schema.sql
cd backend && npm install
DATABASE_URL=postgres://postgres:postgres@localhost:5432/community \
EXPOSE_DEV_CODE=true npm start
```

Для звонков отдельно нужен LiveKit — бинарник берётся с GitHub Releases:

```bash
curl -sL -o livekit.tar.gz \
  https://github.com/livekit/livekit/releases/download/v1.10.0/livekit_1.10.0_linux_amd64.tar.gz
tar xzf livekit.tar.gz && ./livekit-server --dev
```

Версия сервера должна быть не ниже 1.9: с более старыми клиент `livekit-client` 2.x
не публикует микрофон — публикация зависает без ошибки. Без LiveKit работает всё,
кроме звука: экран звонка покажет, что связи нет, и корректно завершит участие.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | `3000` | Порт backend |
| `DATABASE_URL` | `postgres://postgres:postgres@localhost:5432/community` | Подключение к PostgreSQL |
| `JWT_SECRET` | `dev-secret-change-me` | Подпись токенов — **обязательно заменить в проде** |
| `LOGIN_CODE_TTL_SEC` | `600` | Срок жизни кода входа |
| `LOGIN_CODE_COOLDOWN_SEC` | `60` | Rate-limit повторной отправки кода на один email |
| `EXPOSE_DEV_CODE` | `false` (в compose — `true`) | Возврат кода входа в HTTP-ответе. Только для локальной разработки и e2e-прогонов, пока SMTP — заглушка. **В проде должно быть `false`** |
| `ETL_INTERVAL_SEC` | `300` | Как часто пересобираются витрины Silver/Gold. `0` — только вручную (`npm run etl`) и по кнопке на экране аналитики |
| `LIVEKIT_URL` / `LIVEKIT_API_KEY` / `LIVEKIT_API_SECRET` | `ws://localhost:7880` / `devkey` / `secret` | Доступ к LiveKit |

## API

Авторизация — `Authorization: Bearer <token>` из `/auth/verify-code`.

| Метод | Путь | Авторизация | Логика |
|---|---|---|---|
| POST | `/auth/send-code` | — | Генерирует код, пишет в `login_codes`, rate-limit 60 сек/email (429 + `Retry-After`) |
| POST | `/auth/verify-code` | — | Проверяет код (5 попыток, потом код гасится), создаёт/находит пользователя, привязывает `anonymous_id`, выдаёт токен |
| GET | `/users/me` | да | Профиль: почта, имя, скрытие почты |
| PATCH | `/users/me` | да | Меняет имя (`display_name`) и скрытие почты (`hide_email`) |
| GET | `/communities` | да | Сообщества пользователя (для списка в интерфейсе) |
| POST | `/communities` | да | Создаёт сообщество, владельца и два канала (text + voice) |
| GET | `/communities/:id` | да, участник | Сообщество, список каналов и роль запросившего |
| GET | `/communities/:id/members` | да, участник | Состав сообщества: имя, роль, дата вступления |
| PATCH | `/communities/:id` | да, **владелец** | Переименование сообщества (до 60 символов) |
| POST | `/communities/:id/channels` | да, **владелец** | Создаёт текстовый или голосовой канал (до 20 каналов на сообщество) |
| GET | `/communities/:id/analytics` | да, **владелец** | Метрики сообщества из витрин Gold: воронка, WECU, активация, ретеншен, ошибки, активность по дням, длительности |
| POST | `/communities/:id/analytics/refresh` | да, **владелец** | Прогоняет ETL (Bronze → Silver → Gold) и отдаёт пересчитанные метрики |
| POST | `/invites` | да, участник | Создаёт инвайт (`expires_at`, `max_uses` — опционально) |
| GET | `/invites/:id` | — | Превью сообщества для гостя + событие `invite_link_opened` |
| POST | `/invites/:id/join` | да | Вступление в сообщество, инкремент `use_count`, событие `community_joined` |
| POST | `/calls` | да (участник) или гость с `invite_id` | Создаёт звонковую сессию в голосовом канале (одна активная на канал) |
| POST | `/calls/:id/join` | опционально | Добавляет в `call_participants`, выдаёт токен LiveKit, событие `call_joined` с `join_status` |
| POST | `/calls/:id/leave` | опционально | Считает `duration_sec`, событие `call_participated` (только для `user_id`) |
| POST | `/messages` | да, участник | Создаёт сообщение (до 2000 символов), рассылает по WebSocket, событие `message_sent` |
| GET | `/messages?channel_id=` | да, участник | История сообщений |

Гость без регистрации допускается в звонок только по действующему инвайту того
сообщества, которому принадлежит канал — иначе подключение отклоняется, а в
`events_bronze` пишется `call_joined` с `join_status: failed`.

### WebSocket

Подключение: `io('http://localhost:3000', { auth: { token } })` — без валидного
токена соединение отклоняется. События: `join_channel` / `leave_channel`
(с `channel_id`, проверяется членство в сообществе), входящее `message`.

## Аналитика

Все шесть продуктовых событий пишутся в `events_bronze` через общую функцию
`logEvent(type, payload, source)` (`backend/src/lib/events.js`): она генерирует
`event_id` и `timestamp` и сохраняет payload без валидации — по принципу
Bronze-слоя.

События: `invite_link_opened`, `call_joined`, `registration_completed`,
`community_joined`, `message_sent`, `call_participated`.

Сбой записи события логируется, но не ломает пользовательский сценарий.

### Слои: Bronze → Silver → Gold

| Слой | Что это | Где |
|---|---|---|
| Bronze | сырой лог: пишем как пришло, ничего не проверяем | `events_bronze` |
| Silver | очищенный лог: типы разобраны по колонкам, дубли убраны по `event_id`, гость склеен с пользователем, мусор отложен в карантин | `events_silver`, `events_silver_rejected`, `identity_map` |
| Gold | готовые витрины под вопросы экрана | `gold_community_daily`, `gold_community_weekly`, `gold_invite_funnel`, `gold_member_lifecycle`, `gold_call_stats` |

Схема слоёв — `db/analytics-layers.sql`, код ETL — `backend/src/etl/`.

Что делает Silver:

- разбирает payload в типизированные колонки (`silver_uuid` / `silver_int` /
  `silver_ts` возвращают NULL вместо падения на мусоре);
- отклоняет негодное событие с причиной — оно не теряется, а лежит
  в `events_silver_rejected`, так что поломку в коде видно сразу:

  | Причина | Что не так |
  |---|---|
  | `unknown_event_type` | тип события не из шести описанных в спецификации |
  | `bad_uuid` | идентификатор есть, но это не UUID |
  | `no_person` | нет ни `user_id`, ни `anonymous_id` (раздел 6.2 «Полнота») |
  | `bad_enum` | `join_status` не `success` и не `failed` |
  | `unknown_reference` | `community_id` или `invite_id` нет в справочнике |
  | `bad_duration` | длительность отрицательная, нечисловая или больше суток |
  | `bad_timestamp` | время не разбирается или из будущего |
- восстанавливает `community_id` по `channel_id` или `call_id` — в событии
  неудачного подключения его может не быть;
- склеивает личности: `identity_map` связывает `anonymous_id` с `user_id`
  (по событию регистрации и по привязанным записям участия), и уже
  загруженным строкам гостя `person_id` переписывается задним числом.
  Поэтому в воронке гость и он же после регистрации — один человек.

Gold пересобирается целиком на каждом прогоне: данных мало, а полная
пересборка исключает расхождения после приехавших задним числом событий
и после склейки. Берётся блокировка уровня транзакции, так что прогон по
расписанию и прогон по кнопке «Пересчитать» не накладываются.

Запуск ETL:

```bash
cd backend && npm run etl     # разовый прогон с отчётом в консоль
```

Автоматически ETL идёт по расписанию внутри backend: интервал задаётся
`ETL_INTERVAL_SEC` (по умолчанию 300 секунд, `0` — только вручную).
Владелец может пересчитать витрины кнопкой на экране аналитики.

### Где смотреть статистику

В интерфейсе: колонка каналов → раздел «Управление» → «Аналитика»
(`#/c/:id/analytics`). Пункт виден только владельцу сообщества, и сервер
проверяет это сам — прямой переход по адресу отдаёт `403 owner_only`.

Экран показывает вовлечённость за неделю (WECU), активацию в первые сутки,
возврат на 7-й день, долю неудачных подключений к звонку, воронку
приглашения, активность по дням за две недели и длительности звонков.
Цифры читаются из витрин Gold, поэтому экран ничего не вычисляет сам; он
показывает, на какой момент собраны данные, сколько событий ещё в очереди
и сколько отклонено при очистке.

Что метрики честно не учитывают: минуты гостей в звонках (событие участия
пишется только для зарегистрированных — раздел 12.2 спецификации), владельца
в активации и возврате (он не вступал в сообщество), границы суток берутся
по времени сервера базы.

Тем же данным есть и «сырой» доступ — запросами к базе.
Готовый набор лежит в `db/analytics.sql`:

```bash
psql -U postgres -d community -f db/analytics.sql
```

Запросы 1–7 идут по сырому Bronze (годятся, чтобы посмотреть на лог как он
есть), запросы 8–11 — по слоям: состояние Bronze/Silver/Gold, причины
отклонения событий, воронка и WECU из витрин.

Идентификаторы в событиях: `event_id` — ключ самого события (по нему на
Silver убираются дубли), `user_id` — зарегистрированный пользователь,
`anonymous_id` — гость до регистрации, `device_id` — устройство,
`invite_id` / `community_id` / `channel_id` / `call_id` — к чему относится
действие. `invite_id` не уникален: на одно приглашение приходится множество
событий, поэтому в аналитике его использования считаются агрегацией по людям,
а не счётчиком.

## Тесты

Все четыре проверки гоняются автоматически на каждый push и pull request
(`.github/workflows/tests.yml`): GitHub поднимает PostgreSQL, применяет схему,
запускает backend и прогоняет то же, что можно запустить руками ниже. Если
что-то сломалось, в логе шага виден и вывод теста, и лог backend.

Полный сценарий критерия готовности (создание сообщества → инвайт → открытие
гостем → звонок без регистрации → регистрация → вступление в сообщество →
выход из звонка с `duration_sec` → сообщение → проверка всех 6 типов событий):

```bash
PGHOST=localhost PGUSER=postgres PGPASSWORD=postgres ./scripts/e2e-test.sh
```

Проверка реалтайм-доставки по WebSocket:

```bash
cd backend && node scripts/ws-test.mjs
```

Граничные случаи и правила доступа — 30 проверок: кто куда не должен
попадать, что происходит с исчерпанным приглашением, чужим участием
в звонке, слишком длинным сообщением, битым JSON и перебором кода входа:

```bash
./scripts/edge-cases-test.sh
```

Проверка аналитических слоёв на заведомо грязных данных (мусор уезжает
в карантин с правильной причиной, повторный прогон не задваивает, гость
после регистрации становится одним человеком, витрины считаются как
ожидается):

```bash
cd backend && node scripts/etl-test.mjs
```

Первые три скрипта требуют запущенный backend с `EXPOSE_DEV_CODE=true`;
проверке слоёв нужен только доступ к базе — она создаёт временное
сообщество и убирает его за собой.

## Профиль и настройки

Внизу колонки каналов — плашка профиля: имя, статус и меню с настройками,
профилем и выходом.

Имя и скрытие почты хранятся на сервере, потому что их видят другие: в чате и
в звонке вместо почты показывается заданное имя, а при включённом скрытии —
«Участник». Выбор микрофона, камеры и динамиков, звуки и «входить в звонок с
выключенным микрофоном» остаются в браузере: они касаются только этого
компьютера и на сервере никому не нужны.

Разделы «Устройства», «Язык», вход через Госуслуги и двухфакторная защита
показаны с пометкой «скоро» — они есть в макете, но не реализованы.

## Экраны клиента

Хеш-роутинг без сборщика, весь DOM собирается через `el()` с `textContent` —
пользовательский контент не попадает в разметку как HTML.

| Маршрут | Экран |
|---|---|
| `#/login` | Вход по коду на почту |
| `#/` , `#/c/:id` | Главный экран: сообщества, каналы, чат, кнопка «Пригласить» |
| `#/invite/:id` | Превью приглашения для гостя |
| `#/call/:id` | Звонок: плитки участников, микрофон, камера, демонстрация экрана, боковой список, выход с подсчётом длительности |
| `#/settings` | Настройки: имя профиля, приватность, устройства звонка, звуки |
| `#/c/:id/settings` | Сообщество: состав, каналы, название. Менять может владелец |
| `#/c/:id/analytics` | Аналитика сообщества — только для владельца |

Если сервер звонков недоступен, экран звонка это показывает и всё равно
позволяет корректно выйти — участие и `duration_sec` не теряются.

Камера и демонстрация экрана идут через тот же LiveKit и не требуют изменений
в backend. Демонстрация использует `getDisplayMedia`, а он работает только в
защищённом контексте: на `localhost` — да, на боевом сервере — только по HTTPS.

## Как устроен код

Один процесс Node.js отдаёт и API, и клиент. Действие пользователя почти
всегда затрагивает три вещи сразу: состояние в PostgreSQL, событие в
аналитическом логе и, если речь о звонке, соединение с LiveKit.

Подключение к звонку целиком выглядит так: клиент просит у backend токен
(`POST /calls/:id/join`) → backend записывает участника в базу, пишет событие
`call_joined` и отдаёт токен доступа → дальше браузер общается с LiveKit
напрямую, минуя backend. Поэтому звук может не работать, а учёт участия при
этом остаётся корректным — на выходе (`POST /calls/:id/leave`) время всё
равно посчитается.

Гость и пользователь — один и тот же человек на разных стадиях. До
регистрации он существует только как `anonymous_id` в браузере; при вводе
кода backend привязывает его прошлые записи участия к новому `user_id`
(`backend/src/routes/auth.js`), и только потом пишет `registration_completed`.

Каждый файл начинается с комментария о своей зоне ответственности —
начинать чтение удобнее с `backend/src/index.js` и `frontend/js/router.js`.

## Отклонения от спецификации

Все осознанные и по делу, но лучше видеть их списком.

| Что | Как в спецификации | Как сделано и почему |
|---|---|---|
| Лимит использований приглашения | Раздел 6.1 предлагает считать использования агрегацией по событиям, а не счётчиком на записи, из-за гонки | Ограничение проверяется по `use_count` (он же есть в разделах 7 и 12.2) под блокировкой строки `SELECT … FOR UPDATE`: гонки нет, а правило соблюдается точно в момент вступления. В аналитике использования всё равно считаются по людям из событий |
| Камера и демонстрация экрана | Раздел 10: не входит в MVP | Сделано: LiveKit умеет и то, и другое, backend менять не пришлось |
| Слои Silver и Gold | Раздел 6.3: ETL не входит в объём этого этапа | Сделано отдельным шагом после MVP — иначе метрики оставались бы приблизительными |
| Таблица `users` | Раздел 7: id, email, registration_source, created_at | Добавлены `display_name` и `hide_email` — их видят другие участники, значит хранить их надо на сервере |
| Таблица `login_codes` | Раздел 7: без счётчика попыток | Добавлен `attempts`: без него шестизначный код перебирается за время его жизни |
| Таблица `calls` | Раздел 7: без ограничений на параллельные сессии | Добавлен уникальный индекс «один активный звонок на канал» — правило продукта, которое иначе держалось только на проверке в коде |

## Известные ограничения

Про них лучше знать заранее, чем обнаружить их в проде.

| Что | Почему так и чем чревато |
|---|---|
| `anonymous_id` можно подставить чужой | У гостя нет ничего, чем он мог бы себя подтвердить, — это плата за вход в звонок без регистрации. Знающий чужой идентификатор может приписать себе его участие; идентификатор случайный и лежит в чужом браузере, так что подобрать его нельзя, но защиты от целенаправленной подмены нет |
| Гостевой выход из звонка не подтверждается | По той же причине: запрос на выход принимается по `anonymous_id`. У вошедшего пользователя этой дыры нет — его участие ищется только по `user_id` |
| WebSocket не перепроверяет членство | Право на канал проверяется при подписке. Исключения из сообщества в MVP нет, поэтому пересматривать нечего; как только оно появится, подписки нужно будет сбрасывать |
| Нет пагинации истории | Отдаются последние 200 сообщений. Для длинной переписки понадобится подгрузка по мере прокрутки |
| Нет ограничений на создание сообществ и приглашений | Один аккаунт может наплодить их сколько угодно — нужен лимит, если продукт выйдет за пределы своих |
| Звонки в тестах не проверяются по-настоящему | CI прогоняет логику участия и `duration_sec`, но без LiveKit: звук, камера и демонстрация экрана проверяются руками в браузере |
| Минуты гостей не попадают в аналитику | Событие участия пишется только для зарегистрированных (раздел 12.2 спецификации) |

## Что не входит в MVP

Кастомные роли, множественные каналы, стриминг, модерация,
push-уведомления, мобильное приложение.

Камера и демонстрация экрана изначально были отложены спецификацией, но
сделаны: LiveKit умеет и то, и другое, а backend для этого менять не пришлось.
